# Задача 1. Различия между threading, multiprocessing и async в Python

## Описание
Напишите три различных программы на Python, использующие каждый из подходов: threading, multiprocessing и async. Каждая программа должна решать считать сумму всех чисел от 1 до 10000000000000. Разделите вычисления на несколько параллельных задач для ускорения выполнения.

Подробности задания:
1. Напишите программу на Python для каждого подхода: threading, multiprocessing и async.
2. Каждая программа должна содержать функцию calculate_sum(), которая будет выполнять вычисления.
3. Для threading используйте модуль threading, для multiprocessing - модуль multiprocessing, а для async - ключевые слова async/await и модуль asyncio.
4. Каждая программа должна разбить задачу на несколько подзадач и выполнять их параллельно.
5. Замерьте время выполнения каждой программы и сравните результаты.

## Реализация

### Структура проекта

```
task_1/
├── main.py                # Главный скрипт для запуска
├── threading_sum.py       # с использованием threading
├── multiprocessing_sum.py # с использованием multiprocessing
└── async_sum.py           # с использованием async/await
```

### 1. Threading подход (`threading_sum.py`)

**Описание:** Использует модуль `threading` для создания нескольких потоков, каждый из которых вычисляет частичную сумму.

**Ключевые особенности:**
- Легче в использовании, чем multiprocessing
- Работает в одном процессе, разделяя память
- Ограничена GIL (Global Interpreter Lock) в CPython
- Подходит для I/O-bound задач, но не для CPU-bound

**Алгоритм:**
1. Разбить диапазон чисел на N частей (где N = количество ядер ЦП)
2. Создать поток для каждой части
3. Каждый поток вычисляет сумму своей части, используя формулу Гаусса: `(start + end) * count / 2`
4. Объединить результаты от всех потоков

### 2. Multiprocessing подход (`multiprocessing_sum.py`)

**Описание:** Использует модуль `multiprocessing` для создания отдельных процессов, каждый с собственным интерпретатором Python.

**Ключевые особенности:**
- Обходит GIL благодаря отдельным процессам
- Позволяет истинный параллелизм на многоядерных системах
- Большие издержки на создание процессов и межпроцессное взаимодействие
- Подходит для CPU-bound задач (при отсутствии больших данных)

**Алгоритм:**
1. Разбить диапазон на части
2. Использовать `Pool.starmap()` для распределения задач
3. Каждый процесс вычисляет свою сумму независимо
4. Собрать результаты с помощью `gather`

### 3. Async подход (`async_sum.py`)

**Описание:** Использует `asyncio` и `async/await` для создания асинхронных корутин.

**Ключевые особенности:**
- Работает в одном потоке
- Кооперативная многозадачность (не вытесняющая)
- Минимальные издержки переключения
- Идеален для I/O-bound задач
- Может быть неэффективен для CPU-bound при отсутствии блокировок

**Алгоритм:**
1. Разбить диапазон на части
2. Создать асинхронные задачи для каждой части
3. `await asyncio.sleep(0)` вызывает переключение контекста
4. Использовать `asyncio.gather()` для ожидания всех задач

| Async | 8 | 0.000140 | 50000000000005000000000000 |


### 1. Async

**Время:** 0.000140 сек

**Почему так быстро:**
- Работает в одном потоке без реальной параллельности
- `asyncio.sleep(0)` вызывает минимальное переключение контекста
- Нет издержек создания потоков/процессов
- Для CPU-bound задач без I/O это просто добавляет минимальный оверхед

**Вывод:** Async блистательно работает здесь, но это не реальный параллелизм. На практике корутина мгновенно завершается, не имея точек блокировки.

### 2. Threading

**Время:** 0.002131 сек (в 15 раз медленнее, чем async)

**Почему:**
- Издержки на создание 8 потоков (~1-2 мс)
- GIL предотвращает истинный параллелизм для CPU-bound кода
- Потоки могут выполняться истинно параллельно только при блокировке (I/O, системные вызовы)
- Переключение контекста между потоками дороже, чем в async

**Вывод:** Threading эффективнее multiprocessing благодаря низким издержкам, но все еще медленнее, чем async для этой простой вычислительной задачи.

### 3. Multiprocessing

**Время:** 0.232784 сек (в 1663 раз медленнее, чем async)

**Почему:**
- Издержки на создание 8 отдельных процессов (~150+ мс)
- Каждый процесс требует инициализации интерпретатора Python
- Межпроцессное взаимодействие (IPC) имеет высокие затраты
- Для такой простой задачи оверхед намного превосходит выигрыш от параллелизма


### Когда использовать каждый подход:

| Подход | Лучше всего для | Пример |
|--------|-----------------|---------|
| **Async** | I/O-bound задачи | HTTP запросы, чтение файлов, БД запросы |
| **Threading** | I/O-bound с простотой | Веб-скрейпинг, параллельные запросы |
| **Multiprocessing** | CPU-bound (heavy compute) | Обработка изображений, научные вычисления, ML |
